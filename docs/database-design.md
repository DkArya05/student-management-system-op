Database Design — Student Management System

Project: Student Management System — Full Stack Web Application
Document: "docs/database-design.md"
Database: MongoDB
ODM: Mongoose
Architecture: Layered architecture with a Node.js and Express.js backend

1. Introduction

The Student Management System uses MongoDB to store and manage student profiles, user accounts, departments, courses, enrollments, faculty assignments, class sessions, attendance, assessments, and marks.

The database design follows the approved project scope and Day 2 system analysis. It supports the three approved user roles: Administrator, Faculty, and Student.

The design aims to provide:

- Centralized storage of student and academic records.
- Consistent relationships between related documents.
- Validation of required information.
- Prevention of duplicate records.
- Efficient retrieval through appropriate indexes.
- Secure separation of authentication information and student profiles.
- A manageable database structure suitable for a 10-day BCA project.

Important: This document describes the proposed schema and database rules. The final field names, academic rules, and API contracts must be checked against the approved SRS and Day 2 documents before implementation.

2. Database Design Principles

2.1 MongoDB document structure

MongoDB stores information in BSON documents. Mongoose provides schemas, validation, references, and model-based database operations.

Each collection contains documents representing a particular type of entity.

2.2 ObjectId references

Use MongoDB "ObjectId" values for document identifiers and references.

For example:

- "students.departmentId" references "departments._id".
- "enrollments.studentId" references "students._id".
- "attendance.classSessionId" references "classSessions._id".

A reference identifies a related document; it does not automatically enforce a foreign-key constraint. The application must verify that referenced documents exist and that the current user has permission to access them.

2.3 Common fields

The following fields are recommended where applicable:

Field| Data type| Purpose
"_id"| ObjectId| Unique document identifier generated by MongoDB
"createdAt"| Date| Record creation timestamp
"updatedAt"| Date| Last modification timestamp

Mongoose timestamps can maintain "createdAt" and "updatedAt" automatically.

2.4 Conventions

- Use camelCase field names.
- Store dates using BSON Date values, not arbitrary date strings.
- Store monetary values as integer minor units or a consistently defined decimal representation if fees are introduced through an approved scope change.
- Store marks as numbers with explicit maximum-mark validation.
- Use enumerated values for roles, statuses, and attendance states.
- Do not duplicate information unnecessarily across collections.
- Use unique indexes to enforce important uniqueness rules.

3. Collection Overview

Collection| Purpose
"users"| Authentication accounts and user roles
"students"| Student academic and personal profiles
"departments"| Academic department records
"courses"| Course definitions

4. Collection Designs

4.1 Users Collection

Purpose

The "users" collection stores login credentials, account roles, and account status. It is separate from the student academic profile.

Fields and data types

Field| Type| Requirement| Validation
"_id"| ObjectId| Required| Generated by MongoDB
"name"| String| Required| Trimmed; non-empty
"email"| String| Required| Valid email format; normalized to lowercase
"passwordHash"| String| Required| Must contain a bcrypt hash, never a plaintext password
"role"| String| Required| "admin", "faculty", or "student"
"isActive"| Boolean| Required| Defaults to "true"
"createdAt"| Date| Required| Managed by Mongoose timestamps
"updatedAt"| Date| Required| Managed by Mongoose timestamps

References

- A student account may be linked to one document in "students" through "students.userId".
- Faculty assignments refer to faculty profiles through the chosen faculty identity design described in the confirmation section.

Indexes

- Unique index on "email".
- Index on "role" if role-based account queries are frequent.
- Index on "isActive" only if account-status filtering justifies it.

Example document

{
  "_id": "671000000000000000000001",
  "name": "Aarav Kumar",
  "email": "admin@example.com",
  "passwordHash": "$2b$12$exampleBcryptHashValueNotForProduction",
  "role": "admin",
  "isActive": true,
  "createdAt": "2026-10-01T10:00:00.000Z",
  "updatedAt": "2026-10-01T10:00:00.000Z"
}

The password hash above is illustrative and is not a usable credential.

Referential-integrity checks

- Ensure each linked student or faculty account points to a valid user.
- Prevent multiple student profiles from linking to the same user account.
- Prevent duplicate normalized email addresses.
- Do not allow users to assign themselves an Administrator role through public request data.
- When deactivating a user, prevent further protected access through backend authorization checks.

4.2 Students Collection

Purpose

The "students" collection stores student profile and academic identification information.

Fields and data types

Field| Type| Requirement| Validation
"_id"| ObjectId| Required| Generated by MongoDB
"userId"| ObjectId| Optional initially| References "users._id"; unique when present
"studentId"| String| Required| Non-empty, normalized, unique
"fullName"| String| Required| Trimmed; non-empty
"dateOfBirth"| Date| Optional| Must be a valid date and not in the future
"gender"| String| Optional| Only approved values if collected
"phone"| String| Optional| Validated according to the chosen format
"address"| String| Optional| Length-limited
"departmentId"| ObjectId| Required| References "departments._id"
"status"| String| Required| "active", "onLeave", or "inactive"
"createdAt"| Date| Required| Managed by timestamps
"updatedAt"| Date| Required| Managed by timestamps

The optional "userId" allows an administrator to create an academic profile before a login account is linked, if the approved workflow permits it.

References

- "userId" → "users._id"
- "departmentId" → "departments._id"
- Course membership is represented by "enrollments", rather than a duplicated array of course names in each student.

Indexes

- Unique index on "studentId".
- Unique sparse index on "userId", allowing multiple documents without "userId" while preventing duplicate non-null user links.
- Index on "departmentId".
- Compound index on "{ departmentId: 1, status: 1 }" for department-wise status filtering.

Example document

{
  "_id": "671000000000000000000101",
  "userId": "671000000000000000000001",
  "studentId": "BCA2026001",
  "fullName": "Aarav Kumar",
  "dateOfBirth": "2005-05-12T00:00:00.000Z",
  "gender": "male",
  "phone": "9000000001",
  "address": "Ranchi, Jharkhand",
  "departmentId": "671000000000000000000201",
  "status": "active",
  "createdAt": "2026-10-01T10:00:00.000Z",
  "updatedAt": "2026-10-01T10:00:00.000Z"
}

All identifiers are illustrative. Use synthetic student data in development and demonstrations.

Referential-integrity checks

- Confirm the department exists and is active when creating or changing a student profile.
- Confirm a linked "userId" exists and has the correct role.
- Reject duplicate student IDs.
- Prevent a user account from being linked to multiple student profiles.
- When a student becomes inactive, preserve historical enrollments, attendance, and marks unless the approved policy specifies otherwise.

4.3 Departments Collection

Purpose

The "departments" collection stores academic departments such as Computer Applications or Computer Science.

Fields and data types

Field| Type| Requirement| Validation
"_id"| ObjectId| Required| Generated by MongoDB
"departmentCode"| String| Required| Normalized and unique
"name"| String| Required| Non-empty
"description"| String| Optional| Length-limited
"status"| String| Required| "active" or "inactive"
"createdAt"| Date| Required| Managed by timestamps
"updatedAt"| Date| Required| Managed by timestamps

References

Departments are referenced by:

- "students.departmentId"
- "courses.departmentId"

Indexes

- Unique index on "departmentCode".
- Unique index on normalized "name" if department names must be unique under the agreed case-insensitive comparison policy.
- Index on "status" if required for filtering.

Example document

{
  "_id": "671000000000000000000201",
  "departmentCode": "BCA",
  "name": "Computer Applications",
  "description": "Department responsible for the BCA program.",
  "status": "active",
  "createdAt": "2026-10-01T10:00:00.000Z",
  "updatedAt": "2026-10-01T10:00:00.000Z"
}

Referential-integrity checks

- Prevent deleting a department while it is referenced by students or courses, unless a defined reassignment or archival process is completed.
- Verify the department exists before assigning a student or course.
- Prefer deactivation over deletion when historical academic records depend on the department.

4.4 Courses Collection

Purpose

The "courses" collection stores course definitions offered by academic departments.

Fields and data types

Field| Type| Requirement| Validation
"_id"| ObjectId| Required| Generated by MongoDB
"courseCode"| String| Required| Normalized and unique
"name"| String| Required| Non-empty
"departmentId"| ObjectId| Required| References "departments._id"
"description"| String| Optional| Length-limited
"durationYears"| Number| Optional| Positive integer
"status"| String| Required| "active" or "inactive"
"createdAt"| Date| Required| Managed by timestamps
"updatedAt"| Date| Required| Managed by timestamps

References

- "departmentId" → "departments._id"
- Student-course relationships are maintained in "enrollments".
- Faculty-course relationships are maintained in "facultyAssignments".

Indexes

- Unique index on "courseCode".
- Compound index on "{ departmentId: 1, status: 1 }".
- Optional index on "name" if course-name searching requires it.

Example document

{
  "_id": "671000000000000000000301",
  "courseCode": "BCA",
  "name": "Bachelor of Computer Applications",
  "departmentId": "671000000000000000000201",
  "description": "Undergraduate computer applications program.",
  "durationYears": 3,
  "status": "active",
  "createdAt": "2026-10-01T10:00:00.000Z",
  "updatedAt": "2026-10-01T10:00:00.000Z"
}

Referential-integrity checks

- Verify the department exists and is active.
- Do not remove a course that has historical enrollments, faculty assignments, sessions, assessments, or marks without an approved archival or migration policy.
- Confirm a course's department association before updating it.

4.5 Enrollments Collection

Purpose

The "enrollments" collection represents the many-to-many relationship between students and courses.

A student may have enrollments in one or more courses over time, and a course may contain multiple students.

Fields and data types

Field| Type| Requirement| Validation
"_id"| ObjectId| Required| Generated by MongoDB
"studentId"| ObjectId| Required| References "students._id"
"courseId"| ObjectId| Required| References "courses._id"
"academicYear"| String| Required| Approved format, e.g. "2026-2027"
"semester"| Number| Optional| Positive integer if semester-based enrollment is confirmed
"enrollmentDate"| Date| Required| Valid date
"status"| String| Required| "active", "completed", or "withdrawn"
"createdAt"| Date| Required| Managed by timestamps
"updatedAt"| Date| Required| Managed by timestamps

References

- "studentId" → "students._id"
- "courseId" → "courses._id"

Indexes

- Unique compound index on "{ studentId: 1, courseId: 1, academicYear: 1 }" if only one enrollment per student, course, and academic year is allowed.
- Compound index on "{ courseId: 1, status: 1 }".
- Compound index on "{ studentId: 1, status: 1 }".

If semester-level re-enrollment is permitted within the same academic year, the unique index must include "semester" or follow the confirmed enrollment policy.

Example document

{
  "_id": "671000000000000000000401",
  "studentId": "671000000000000000000101",
  "courseId": "671000000000000000000301",
  "academicYear": "2026-2027",
  "semester": 1,
  "enrollmentDate": "2026-10-01T10:00:00.000Z",
  "status": "active",
  "createdAt": "2026-10-01T10:00:00.000Z",
  "updatedAt": "2026-10-01T10:00:00.000Z"
}

Referential-integrity checks

- Confirm the student and course exist.
- Confirm the student and course are eligible for enrollment.
- Prevent duplicate enrollments according to the agreed academic-year and semester policy.
- Verify that historical attendance and marks remain linked to the correct student and course.
- Do not assume the course stored in the student's department is identical to an enrollment; validate the approved department/course rules.

4.6 FacultyAssignments Collection

Purpose

The "facultyAssignments" collection associates faculty members with courses they are authorized to teach.

Fields and data types

Field| Type| Requirement| Validation
"_id"| ObjectId| Required| Generated by MongoDB
"facultyUserId"| ObjectId| Required| References "users._id"
"courseId"| ObjectId| Required| References "courses._id"
"academicYear"| String| Required| Approved academic-year format
"semester"| Number| Optional| Positive integer if applicable
"status"| String| Required| "active" or "inactive"
"assignedAt"| Date| Required| Valid date
"createdAt"| Date| Required| Managed by timestamps
"updatedAt"| Date| Required| Managed by timestamps

References

- "facultyUserId" → "users._id"
- "courseId" → "courses._id"

This design uses the faculty member's account as the assignment identity. If a separate faculty profile collection is later approved, the reference should be revised consistently.

Indexes

- Compound index on "{ facultyUserId: 1, status: 1 }".
- Compound index on "{ courseId: 1, academicYear: 1, semester: 1 }".
- Unique compound index on "{ facultyUserId: 1, courseId: 1, academicYear: 1, semester: 1 }" if only one assignment per faculty/course/period is allowed.

If "semester" is optional, define a consistent storage policy or a partial unique index so missing semester values do not create unintended duplicate behavior.

Example document

{
  "_id": "671000000000000000000501",
  "facultyUserId": "671000000000000000000002",
  "courseId": "671000000000000000000301",
  "academicYear": "2026-2027",
  "semester": 1,
  "status": "active",
  "assignedAt": "2026-10-01T10:00:00.000Z",
  "createdAt": "2026-10-01T10:00:00.000Z",
  "updatedAt": "2026-10-01T10:00:00.000Z"
}

Referential-integrity checks

- Confirm the referenced user exists, is active, and has the "faculty" role.
- Confirm the course exists and is active.
- Check assignment authorization before allowing attendance or marks operations.
- Do not allow inactive assignments to authorize new attendance or marks changes.
- Preserve historical assignment references when records depend on them.

4.7 ClassSessions Collection

Purpose

The "classSessions" collection records individual class sessions for which attendance may be recorded.

Fields and data types

Field| Type| Requirement| Validation
"_id"| ObjectId| Required| Generated by MongoDB
"courseId"| ObjectId| Required| References "courses._id"
"facultyAssignmentId"| ObjectId| Required| References "facultyAssignments._id"
"sessionDate"| Date| Required| Valid date
"startTime"| String| Optional| Valid agreed time format
"endTime"| String| Optional| Valid agreed time format; after start time
"topic"| String| Optional| Length-limited
"status"| String| Required| "scheduled", "completed", or "cancelled"
"createdAt"| Date| Required| Managed by timestamps
"updatedAt"| Date| Required| Managed by timestamps

References

- "courseId" → "courses._id"
- "facultyAssignmentId" → "facultyAssignments._id"

Indexes

- Compound index on "{ courseId: 1, sessionDate: -1 }".
- Compound index on "{ facultyAssignmentId: 1, sessionDate: -1 }".
- Add a unique session identifier only if the approved scheduling rules define a reliable uniqueness key. Do not assume that two sessions on the same course and date are always duplicates.

Example document

{
  "_id": "671000000000000000000601",
  "courseId": "671000000000000000000301",
  "facultyAssignmentId": "671000000000000000000501",
  "sessionDate": "2026-10-05T00:00:00.000Z",
  "startTime": "10:00",
  "endTime": "11:00",
  "topic": "Introduction to JavaScript",
  "status": "completed",
  "createdAt": "2026-10-05T04:00:00.000Z",
  "updatedAt": "2026-10-05T04:00:00.000Z"
}

Referential-integrity checks

- Confirm the course exists.
- Confirm the faculty assignment exists and belongs to the same course.
- Confirm the assignment is active for the session's academic period.
- Prevent attendance recording for cancelled sessions.
- Apply the institution's date and time-zone conventions consistently.

4.8 Attendance Collection

Purpose

The "attendance" collection stores attendance records for individual students and class sessions.

Fields and data types

Field| Type| Requirement| Validation
"_id"| ObjectId| Required| Generated by MongoDB
"studentId"| ObjectId| Required| References "students._id"
"classSessionId"| ObjectId| Required| References "classSessions._id"
"status"| String| Required| "present", "absent", or "late"
"recordedBy"| ObjectId| Required| References "users._id"
"recordedAt"| Date| Required| Valid timestamp
"remarks"| String| Optional| Length-limited
"createdAt"| Date| Required| Managed by timestamps
"updatedAt"| Date| Required| Managed by timestamps

References

- "studentId" → "students._id"
- "classSessionId" → "classSessions._id"
- "recordedBy" → "users._id"

Indexes

- Unique compound index on "{ studentId: 1, classSessionId: 1 }".
- Compound index on "{ classSessionId: 1, status: 1 }".
- Compound index on "{ studentId: 1, recordedAt: -1 }".

The unique compound index prevents duplicate attendance documents for the same student and class session.

Example document

{
  "_id": "671000000000000000000701",
  "studentId": "671000000000000000000101",
  "classSessionId": "671000000000000000000601",
  "status": "present",
  "recordedBy": "671000000000000000000002",
  "recordedAt": "2026-10-05T05:00:00.000Z",
  "remarks": "",
  "createdAt": "2026-10-05T05:00:00.000Z",
  "updatedAt": "2026-10-05T05:00:00.000Z"
}

Referential-integrity checks

- Confirm the student exists and is eligible for the session.
- Confirm the class session exists and is not cancelled.
- Confirm the recording user is authorized to record attendance for that class.
- Prevent duplicate attendance using the unique index and handle duplicate-key errors.
- Ensure attendance percentages are calculated from valid attendance records and the approved calculation rules.
- Restrict Students to viewing their own attendance records.
